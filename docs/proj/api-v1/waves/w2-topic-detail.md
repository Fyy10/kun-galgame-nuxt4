## 1. 普查结论（2026-09-19，代码 + 生产库）

旧路径：`GET /api/topic/:tid`（详情）、`/reply`（回复页码列表）、`/reply/detail`（引用悬停）、`/reply/locate`（楼层 → 页码），逐字段表在派发报告里。影响设计的事实：

- **楼层**：创建时取 `MAX(floor)+1`，不加锁，没有唯一约束，删除不重排。生产库：1 组重复楼层（2 行），75 个话题有空号，3 条隐藏回复（`status=1`）。`topic_reply` 上没有 `(topic_id, floor)` 索引，按楼层排序与定位都在扫表。
- **置顶与最佳答案**：旧列表只在第 1 页把它们插到最前，并从后续各页剔除，所以第 1 页可能有 limit+2 条；`locate` 按 `floor<=N` 计数（含隐藏行、含置顶），算出的页码与列表对不上。最佳答案的内嵌不看 `status`，隐藏的最佳答案仍会出现在详情里。生产库 103 个话题设了最佳答案、24 个置顶，都指向可见的回复。
- **末页判断**：网页按「本页不足 30 条」判末页，置顶把第 1 页撑满或封禁作者把整页剔短时都会错。
- **可见性**：详情、回复列表、单条回复都用同一个读判定（隐藏 → 仅作者与 cookie staff；`access_scope` → login / role / users；作者封禁 → 404）。NSFW 在 API 层不过滤，网页对匿名 SFW 访客用确认卡遮挡。
- **浏览数**：每个 GET 详情都 +1（`topic.view` 与日桶表），不去重；SSR 与分享卡片（OG）各打一次，爬虫也算。
- **评论**：每条回复内嵌全部评论（生产最多 22 条，P99 9 条），纯文本，客户端按 `parent_comment_id` 成树；评论作者被封禁时旧接口发占位名 + 空内容。
- **表情**：`topic_reaction` 与 `topic_reply_reaction` 同表存 like / dislike 与其余 31 种表情；`like_count` 与 reactions 里的 like 项是同一份数据。代码的词表是 33 个 token，库里用到 31 个。
- **萌萌点**：作者卡片显示本站缓存的萌萌点，可以为负（生产 25 人，最低 −16）。
- 旧读路径没有任何 HTTP 或 DB 测试。

## 2. 裁决

**四个操作**（全部 `optional` 档）：

| 操作 | 说明 |
|---|---|
| `GET /topics/{topic_id}` → `Topic` | 只读，不计浏览 |
| `GET /topics/{topic_id}/replies` → `List<Reply>` | 游标，按楼层 |
| `GET /replies/{reply_id}` → `Reply` | 引用悬停；也是 W4 回复互动写路径的 G17 前提 |
| `POST /topics/{topic_id}/views` → 204 | 浏览信标 |

- **浏览数改为信标**（用户 2026-09-19 拍板）：GET 不再有副作用；网页（与 App）在读者真正打开话题时调一次 `POST …/views`。SSR、分享卡片、预取、不执行 JS 的爬虫从此不计数，增长会比现在慢，但更接近真实阅读。
  - 信标允许匿名，所以不带幂等键，是 K12「全部 POST 支持幂等键」的具名例外：重复发送的后果与刷新页面相同。
  - 路由表测试 `publicWrites` 对 v1 也生效，登记了它。
- **不可见一律 `NOT_FOUND`**：话题不存在、隐藏且调用方不是作者或 staff、不在 `access_scope` 允许的读者之列、作者被封禁，四种情况不可区分，不泄露存在性。
  - Bearer 请求没有 staff 能力（K2），隐藏话题只有作者本人能读。
- **置顶与最佳答案作为 `Topic` 的字段**（`pinned_reply`、`best_answer`，完整 `Reply` 或 `null`）。它们在回复集合里也照常出现在自己的楼层，列表不再插队，客户端在顶部单独展示。隐藏或作者被封禁 → `null`。
- **楼层定位用锚点，不再算页码**：`from_floor` + `sort=floor_asc|floor_desc`，同一种游标（01 §4 预留的形态）。
  - 打开第 N 楼：`from_floor=N`。
  - 往前加载：`sort=floor_desc&from_floor=N-1`。
  - 游标绑定排序、锚点与话题。排序键 `(floor, id)`，重复楼层也稳定。
  - 按评论定位（`?comment=`）属于评论域，W5 前网页继续用旧 `locate` 拿楼层，再走 v1 锚点。
- **隐藏回复对所有人不可见**（与旧列表一致，作者与 staff 也看不到）；作者被封禁的回复不下发，服务端向后读满一页（与话题列表同一机制）。
- **评论内嵌在 `Reply.comments`**，字段 `text`（纯文本；`content` 是正文文档的名字，同名不同型违反 A4）。被评论的人按角色命名为 `in_reply_to_user`。作者被封禁的评论不下发，子评论保留自己的 `parent_comment_id`，客户端把找不到父级的评论当作顶层。
- **表情是开放词表**（`x-vocabulary: reaction`，pattern `^[a-z][a-z0-9_]*$`）：词表会增长，客户端对未知 token 用中性占位。`reactors` 至多 3 人、跳过封禁用户，`count` 仍是总数。查看者是否点过放在嵌套的 `viewer.has_reacted`（K9）。
- **`author_moemoepoint`**：与旧版一致展示本站缓存的萌萌点，有符号整数。不放进 `UserRef`：`author` 在话题列表里是 `UserRef`，改成别的 schema 会违反 G8。
- **`viewer` 进 G8 例外**：K9 要求每种资源各带自己的 `viewer`，字段必然不同（话题有收藏 / 推，评论只有点赞），与 `object`、`state` 同理。
- **不在 W2**：
  - `access_grants`、正文源文 `content_markdown`：编辑语境，W3 给作者与编辑者单独的读取；W2 期间网页编辑时仍向旧详情取；
  - `can_*`：随对应写操作在 W3 / W4 加；
  - 投票、抽奖、推记录、表情历史：W4 / W5。
- **迁移 097**：`topic_reply (topic_id, floor, id)` 索引，服务列表与锚点。只加索引，部署顺序无关。重复楼层与建楼层的竞态属于回复写面（W3），那时再加唯一约束与加锁。

## 3. 门的变化

- **F10（新）**：路径模板里的每个 `{变量}` 必须恰有一个同名 `in: path` 参数，反之亦然。
  - 起因：契约初稿把路径参数写在未导出类型的嵌入结构体里，huma 静默丢掉了它。`/topics/{topic_id}` 于是没有参数，也没推导出 400，而其余每道门都放行了。
  - 阳性对照复现了这个写法。

## 4. 验收（2026-09-19）

| 派发 | 范围 | 用时 |
|---|---|---|
| `w2-go` | 四个操作的实现、共享读判定 `internal/topic/access`、迁移 097、DB 契约测试 | 2466 秒，443 次调用 |
| `w2-web` | 话题页切到 v1、回复游标状态、纯文本工具、OG 卡片、旧写操作回落到 v1 状态 | 2106 秒，351 次调用 |

**Go**：沙箱没有数据库，10 个 DB 契约测试是验收时第一次跑，7 个直接通过，3 个失败。3 个都是测试本身的错：

- 两处把查看者标记解码进了没有 json 标签的字段，驼峰字段名永远匹配不上 `has_liked`；
- 「没有授权的调用者」用的是话题作者本人，作者恒可读。「角色已授权」那条同样用了作者，所以什么也没证明，改用非作者。

验收另外修了：

- **回复页读窗口**：初版只要还有更多行，就把 5 个窗口全读完，再给 150 条回复加载评论与表情，只为展示 30 条。改成按窗口核作者、凑满即停，并加了数窗口的 DB 测试。
- **浏览信标**：日桶写失败时不再返回 204 吞掉错误。
- **图片元数据**：测试钩子并进 App 上唯一的依赖字段。
- **封禁作者判断**：删掉 `buildTopic` 里重复的一次。

变异：DB 测试能跑之后，13 个变异里 11 个被杀。存活的两个：

- 「按角色给 staff」：Bearer 的角色已在 `bearer.go` 剥掉，两道防线重叠，属等价变异；
- `get.go` 的重复判断：已删。

**网页**：

- 已修：
  - 非 404 的读失败给出错误与重试，而不是「未找到」；
  - 按最新排序时，新回复插到最前；
  - 悬停预览不再永久缓存失败；
  - 已注销的标签移到 `shared`，Nitro 不再引用 `app/`；
  - 两个客户端改在 setup 里取。
- 已知未改：收藏、推、评论点赞的计数只更新按钮内的状态，不回写页面上的 v1 对象。与现行一致，刷新话题后以服务端为准。

**真浏览器（dev 栈，匿名 + 临时会话）**：

- SSR 渲染；水合不重复请求；置顶与最佳答案在列表上方各出现一次，列表里剔除；元素 id 无重复。
- 楼层：`?reply=50` 从 50 楼开始并滚动到位；「加载更早」发 `floor_desc&from_floor=49`，把 20–49 楼按升序插到前面；加载更多到 60 楼；「最新」排序从 109 楼倒序。
- 标题锚点为中文 slug。
- 楼层引用悬停只发一次 `GET /api/v1/replies/{id}`；@ 点击跳用户页；不存在的话题显示空态。
- **浏览数**：3 次 API 读 +0，SSR +0，一次真实打开 +1，切换排序 +0。
- **登录态**：点赞走旧写，v1 读回 `viewer.has_liked` 与表情项，撤销复原；发回复后 v1 重新读取并出现在 28 楼；发评论后回复刷新出现评论；删除回复后从列表移除，v1 返回 404；编辑回复打开时从旧接口取到源文。测试数据已全部删除。
- 加载中后退：点进话题、v1 详情请求尚在途时后退，`/topic` 正常渲染 50 条。

迁移 097 只加索引，部署时自动执行。
